## 目标和边界

用户批准建立一次授权、以后无需反复登录 Workbench 的发布流程。以 `3107c42` 为起点，隔离分支 `codex/automated-web-release-2026-09-08` 实施；首次发布包括此前 G-Mark 更正。不改原工作树、默认分支、API、数据库、上传卷、证书或现有管理员认证。

正式发布分支采用独立 `production`，由通过 CI 的当前开发提交建立；生产环境 `ecs-production` 只允许该分支，禁止任意开发分支或 PR 使用部署凭据。CI 仍在 GitHub 托管机器执行，正式服务器不安装通用 Actions runner。

## 接口与安全

- 在真实浏览器测试成功后，打包该次确切 SHA 的公开 dist；包含 `release.json`，记录 SHA、全部文件大小和 SHA-256。
- 专用用户 `fwx-deploy` 使用 SSH 强制命令，只接受 `status`、`publish <SHA> <archive-sha256>`、`rollback <SHA>`。发布压缩包通过标准输入传输；回退只允许当前 SHA 的上一版本。
- 密钥存 GitHub 生产环境 Secrets；主机密钥必须与已信任 known_hosts 或服务器人工读取的公钥一致，禁止关闭主机验证。不开放 Docker 组、任意 sudo、交互 shell 或转发。
- root 拥有的固定发布器与配置不从上传包更新。拒绝目录穿越、链接、特殊文件、重复路径和隐藏凭据；限制压缩 256 MiB、解压 512 MiB、10000 条目及接收时间。只在全新 root-owned 目录解包，不覆盖 live dist。
- 固定 Compose 快照只允许切换 nginx；API/Mongo 身份必须保持。配置、公开入口/资源和 API 检查失败时回退，串行锁避免并发切换。保留旧目录，禁止自动删库或清理用户数据。

## 顺序与验收

1. 测试先行实现归档、受限 SSH、服务器发布和恢复逻辑；本地隔离测试成功后独立安全复核。
2. 完整 Harness/CI，核对 GitHub 当前 SHA 全部作业结果；准备哈希固定的首次安装指令。
3. 通过 GitHub API 配置专用生产环境、分支约束和部署凭据。首次服务器初始化必须由用户在 Workbench 执行；当前浏览器工具禁止该网址，不能绕过。
4. 真实 SSH 核验身份限制、拒绝任意命令、状态和已信任主机密钥；网络不通或身份不符则停止，不盲目放宽防火墙。
5. 首次自动发布后核验线上 SHA/摘要、前三奖项/数量/图片、三个视口与 API 健康，验证故障回退与前后 API/Mongo 不变。
6. 更新当前状态、部署说明与接续入口。只有真实服务器与公网站点验证完成才把计划标为完成。
